# RCA — "Published app having issues logging in" (auto-trader-pro-3 / AI's Elite PO Traders Bot)

**Deployment:** auto-trader-pro-3  •  **Active run:** c19174ad-4aab-4bf2-a24e-4e9098f885c6 (redeploy, success)
**Prod URL:** https://auto-trader-pro-3.emergent.host  •  Custom domains (verified): elitepotradingbot.com, www.elitepotradingbot.com
**Template:** fastapi_react_mongo_shadcn (farm)  •  **Frontend:** Cloudflare  •  **Tier:** tier_1 (Launch), 2 replicas, cpu 250m/500m, mem 1Gi/2Gi

## Verdict
This is **NOT** a missing/mangled env var, a JWT bug, a seed-admin seeding failure, a wrong backend URL in the React bundle, a Mongo binding problem, or a CORS issue. All of those were checked and are healthy (see below).

**Root cause: the FastAPI backend's request-serving path is saturated/blocked by heavy in-process background trading-bot work, so the entire `/api/*` surface times out — including `/api/auth/login`.** The login page loads (served from Cloudflare), but the login *request* never completes → users experience it as "can't log in."

## Evidence
1. **Whole `/api` surface is unresponsive, not just login.**
   - `GET /api/auth/login` → timeout, `context deadline exceeded` at 15,001 ms.
   - `GET /api/` → timeout, `context deadline exceeded` at 15,000 ms.
   - `GET /` and `GET /health` → **200 in 235 ms / 511 ms** (these are served by Cloudflare from R2 as the SPA, so they do NOT exercise the backend). The fast frontend + timing-out API is the classic signature of a saturated backend behind a healthy edge.

2. **Pod is healthy — this is not a crash/OOM/boot failure.**
   - Pod `Running`, `restart_count: 0`, started 2026-09-29T08:41Z (>1 day stable), no OOMKilled, no CrashLoopBackOff, no evictions, `kill_findings: []`.

3. **Backend process is alive but CPU-saturated by background workers.** Runtime logs (last 4h) are a continuous flood of in-process background work, e.g.:
   - `ml_accuracy_tuner - INFO - OTC CV scores: [...]`, `ml_accuracy_tuner - ... samples from 500 candles`
   - `flexible_crossover_strategy - INFO - Fetching 1m data for ...` / `Strategy initialized` across dozens of FX/OTC pairs every ~16s
   - 107 error lines, all from market-data scraping (`yfinance - ERROR - Failed to get ticker ... Impersonating chrome136 is not supported`, `possibly delisted`, OANDA `401 Insufficient authorization`).
   - There is **zero** auth/login/bcrypt/JWT/Mongo output in the window — login requests aren't even reaching a handler; they're queued behind blocking work.
   - tier_1 CPU limit is **500m** (half a core) per replica; sustained ML/scraping/scanning at this ceiling leaves the asyncio event loop no room to serve HTTP.

4. **All env vars present and correct (values never revealed):**
   - `MONGO_URL`, `DB_NAME`, `JWT_SECRET`, `SEED_ADMINS` — all exist, none empty. So no `KeyError`/mangling/empty-string startup problem.
   - `REACT_APP_BACKEND_URL` → **matches** `https://elitepotradingbot.com` (the verified custom domain). The bundle is NOT pointing at a preview URL. Ruled out.
   - `CORS_ORIGINS` → **matches** `*`. No CORS/CSRF block.

5. **Mongo bound; seed admin correctly present & active.** DB `auto-trader-pro-3-trading_bot_db`, 68 collections incl. `users`. Seed admin doc:
   - `email: seedtest@elitepo.com`, `is_active: true`, `role: admin`, `status: active`, `username: seedtest`, `password_hash: "hmac:..."` (app uses **HMAC**, not bcrypt — the bcrypt concern is moot).
   - Seeding on startup is working. The `ACCOUNT_PENDING` / approval workflow is not blocking this account.

## Secondary findings (not the cause of the timeout, but will bite once the API is responsive)
- **`testuser` does NOT exist in the prod `users` collection.** Only `seedtest` is present. The grandfathered `testuser/test123` is a preview-only account — logging in with it on prod will return invalid-credentials even after the timeout is fixed. Test prod with the seed admin (`seedtest@elitepo.com`) instead.
- **`newadmin@elitepo.com` is not seeded** and the stored `SEED_ADMINS` value does **not** match the string quoted in the request (`seedtest@...:...,newadmin@...:...`). The `seedtest` admin is still active, so admin login works — but if `newadmin` is required, the stored `SEED_ADMINS` needs to be corrected (Deployment Panel → Secrets) and the app redeployed/restarted. Worth confirming the stored value wasn't shell-mangled/truncated, though it did not break `seedtest`.

## Fix (owned by app source — E1)
**Primary (Code):** Get the heavy background trading-bot work off the web request path.
- Move the schedulers/loops (yfinance scraping, `ml_accuracy_tuner`, `flexible_crossover_strategy` scanning, OANDA polling) out of the FastAPI/uvicorn process into a **separate worker process/service**, OR
- If they must stay co-located, run all blocking/CPU-bound calls via `run_in_executor`/a threadpool or a subprocess, cap concurrency, and add backoff so they cannot starve the event loop.
- Also throttle/short-circuit the failing market-data fetches (chrome136 impersonation errors, delisted tickers, OANDA 401) — they're running hot in a tight retry loop and adding to the load.
- **Verify:** after the change, `GET /api/` and a `POST /api/auth/login` should respond in well under 1s under normal background load.

**Note on tier:** simply raising the tier is unlikely to fully resolve this if the work blocks the single asyncio event loop — more CPU doesn't unblock a blocked loop. Fix the architecture first; a tier bump can be a mitigation but is not the root fix and CPU-throttling could not be metric-confirmed here.

**Secondary (User/data):** Decide/seed the accounts you intend to test on prod (`testuser` is not in prod; correct `SEED_ADMINS` if `newadmin` is needed), then redeploy so startup seeding re-runs.

## Explicitly ruled out
Missing/empty/mangled env var • wrong DB name • Mongo not bound • seed-admin never seeded • dollar-sign shell-expansion breaking the seed admin • wrong backend URL baked into the React bundle • CORS/CSRF • bcrypt/passlib • pod crash/OOM/CrashLoop.
